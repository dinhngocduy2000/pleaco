You are implementing the first realtime robot-connectivity flow for **Pleco — Realtime Autonomous Cleaning Robot Platform**.

The goal is to simulate autonomous cleaning robots connecting to the platform over **MQTT using Eclipse Mosquitto**, propagate robot connectivity events into the backend through **RabbitMQ**, maintain live state in **Redis**, persist durable state in **PostgreSQL**, and update the React frontend in realtime through **WebSockets**.

This milestone comes before map creation and should establish Pleco's first complete realtime device-to-UI pipeline.

## Objective

Implement this end-to-end flow:

```text
Robot Simulator
      │
      │ MQTT
      ▼
Eclipse Mosquitto
      │
      ▼
MQTT Ingestion Service
      │
      │ Internal event
      ▼
RabbitMQ
      │
      ▼
Robot Status Consumer
      │
      ├── Redis
      ├── PostgreSQL
      └── WebSocket
             │
             ▼
         React Client
```

The first supported use case is robot connectivity only:

```text
OFFLINE → ONLINE
ONLINE  → OFFLINE
```

Do not implement movement, cleaning execution, position telemetry, heading, velocity, task progress, map navigation, collision handling, or other robot behavior yet.

# 1. Robot Identity

Every robot must use its existing Pleco UUID as the canonical identifier.

```text
robot_id
→ stable unique robot identity
```

The robot IP address must not be used as the primary identity.

```text
ip_address
→ mutable network metadata
```

This distinction is mandatory.

Example:

```text
robot_id
→ identifies which registered Pleco robot sent the message

ip_address
→ reports the robot's current network address
```

A robot can change IP address without changing identity.

---

# 2. Existing Robot Domain

Pleco already supports robot registration and robot inventory.

Assume a robot contains at least:

```text
id
group_id
serial_num
name
model
map_id
ip_address
connection_status
operational_status
last_seen_at
created_at
updated_at
```

Important rules:

```text
id
→ UUID primary key

serial_num
→ unique within a group

group_id
→ robot belongs exclusively to one group

map_id
→ nullable
→ one robot can belong to at most one map

connection_status
→ ONLINE | STALE | OFFLINE

operational_status
→ IDLE | CHARGING | EXECUTING
```

Newly registered robots initially have:

```text
connection_status = OFFLINE
operational_status = IDLE
```

Connectivity and operational state must remain separate.

# 4. MQTT Topic Design

Use the Pleco robot UUID in MQTT topics.

Connectivity topic:

```text
pleco/robots/{robot_id}/status
```

Example:

```text
pleco/robots/7a3c2f9d-0cc4-4aef-a093-.../status
```

Do not use the IP address in place of the robot UUID.

Avoid designs such as:

```text
pleco/robots/192.168.10.24/status
```

because IP addresses are mutable.

# 5. Standard MQTT Message Envelope

Robot messages should follow a consistent envelope.

Use at least:

```text
message_id
robot_id
ip_address
event
sequence_number
timestamp
```

Responsibilities:

```text
robot_id
→ which robot sent the event

ip_address
→ current network metadata reported by the robot

message_id
→ uniquely identifies this individual message

sequence_number
→ ordering of messages from this robot

timestamp
→ when the event occurred

event
→ what happened
```

Example:

```json
{
  "message_id": "8af8d6d2-bbc4-4e78-9c66-4579c2cf9cd3",
  "robot_id": "7a3c2f9d-0cc4-4aef-a093-94ee3b584ec7",
  "ip_address": "192.168.10.24",
  "event": "robot.online",
  "sequence_number": 42,
  "timestamp": "2026-08-24T07:20:00Z"
}
```

Use UTC ISO-8601 timestamps.

`message_id` should preferably be a UUID generated by the robot simulator.

`sequence_number` should increase monotonically for messages produced during the robot session.

# 6. ONLINE Status Message

After successfully connecting to Mosquitto, the simulator publishes:

```text
Topic:
pleco/robots/{robot_id}/status
```

Example ONLINE payload:

```json
{
  "message_id": "f3ba6b56-8f54-4854-8a91-94b240022161",
  "robot_id": "7a3c2f9d-0cc4-4aef-a093-94ee3b584ec7",
  "ip_address": "192.168.10.24",
  "event": "robot.online",
  "sequence_number": 1,
  "timestamp": "2026-08-24T07:20:00Z",
  "data": {
    "connection_status": "ONLINE"
  }
}
```

The ONLINE event means:

```text
The robot successfully established its MQTT session
and is currently reachable through the device messaging layer.
```

It does not mean the robot is executing a task.

The expected resulting state may therefore be:

```text
connection_status = ONLINE
operational_status = IDLE
```

# 9. MQTT Last Will and Testament

Support unexpected disconnection using MQTT LWT.

Before connecting, configure the simulator's Last Will on:

```text
pleco/robots/{robot_id}/status
```

The LWT payload should identify the same robot UUID.

Example:

```json
{
  "message_id": "GENERATED_FOR_LWT",
  "robot_id": "7a3c2f9d-0cc4-4aef-a093-94ee3b584ec7",
  "ip_address": "192.168.10.24",
  "event": "robot.offline",
  "sequence_number": 54,
  "timestamp": "BEST_AVAILABLE_EVENT_TIME",
  "data": {
    "connection_status": "OFFLINE"
  }
}
```

Because an LWT payload is normally configured before the unexpected failure actually happens, do not rely on the LWT timestamp alone as an authoritative disconnect timestamp if the MQTT client cannot update it dynamically.

The backend may use its receive time as the effective offline detection time where appropriate.

LWT should cover cases such as:

```text
process crash
network failure
container kill
machine shutdown
```

# 11. MQTT Ingestion Service

Create a backend-side MQTT ingestion component or worker.

Responsibilities:

1. Connect to Mosquitto.
2. Subscribe to:

```text
pleco/robots/+/status
```

3. Receive raw robot messages.
4. Extract the robot UUID from the MQTT topic.
5. Validate the JSON payload.
6. Compare the topic robot ID with `payload.robot_id`.
7. Reject inconsistent identities.
8. Normalize the message into an internal Pleco event.
9. Publish that event to RabbitMQ.

Example invalid message:

```text
Topic:
pleco/robots/ROBOT-A/status
```

Payload:

```json
{
  "robot_id": "ROBOT-B"
}
```

This must be rejected.

The MQTT ingestion service should primarily perform:

```text
MQTT
    ↓
validation
    ↓
identity verification
    ↓
normalization
    ↓
RabbitMQ
```

Do not make the frontend subscribe directly to MQTT.

Prefer keeping database/cache mutation outside this ingestion layer.

# 13. Robot Status Consumer

Create a RabbitMQ consumer responsible for processing robot status events.

The consumer must:

1. Validate the internal event.
2. Resolve the robot using `robot_id`.
3. Reject or safely ignore unknown robots.
4. Treat the robot UUID as canonical identity.
5. Treat IP address as mutable metadata.
6. Check current state in Redis.
7. Fall back to PostgreSQL if Redis misses.
8. Update Redis/PostgreSQL only when appropriate.
9. Update the stored IP address if the implementation considers the reported IP authoritative.
10. Emit a WebSocket event for meaningful changes.

Do not resolve robots primarily by IP address.

# 14. Redis + PostgreSQL State Strategy

Use:

```text
Redis
→ current/live robot state

PostgreSQL
→ durable last-known robot state
```

Processing algorithm:

## Redis hit

If a Redis state exists:

```text
Compare cached status
against incoming status
```

If identical:

```text
Do not update PostgreSQL.
Do not unnecessarily rewrite the same state.
```

If different:

```text
Update Redis.
Update PostgreSQL.
Publish WebSocket event.
```

## Redis miss

Read persisted state from PostgreSQL.

If PostgreSQL already matches:

```text
Seed Redis.
Do not perform an unnecessary PostgreSQL UPDATE.
```

If PostgreSQL differs:

```text
Update PostgreSQL.
Write Redis.
Publish WebSocket event.
```

Core behavior:

```text
Redis hit + same
→ do nothing

Redis hit + different
→ Redis + PostgreSQL + WebSocket

Redis miss + DB same
→ Redis only

Redis miss + DB different
→ PostgreSQL + Redis + WebSocket
```


# 17. Duplicate Message Handling

Use `message_id` to distinguish individual messages.

If the same `message_id` is received again:

```text
Do not apply the event twice.
```

At minimum, processing must be idempotent based on current state.

Design the implementation so explicit message deduplication can be extended later.

---

# 18. Sequence Numbers and Ordering

Use `sequence_number` to help detect out-of-order messages from the same robot.

Example:

```text
Current processed sequence:
42

Incoming:
43
→ valid

Incoming:
41
→ stale
```

An older message must not overwrite newer robot state.

Example:

```text
sequence 100 → ONLINE
sequence 99  → OFFLINE arrives afterward
```

The sequence 99 event should be ignored as stale.

Timestamp checks may be used as an additional safeguard, but sequence ordering should be preferred when available and valid.

This may use the event timestamp or backend receive time according to existing project conventions.

Do not update `last_seen_at` from rejected, malformed, duplicate, or stale messages.

Future high-frequency telemetry persistence optimization is out of scope.

# 21. Group Isolation

Pleco uses group-level isolation.

A robot belongs exclusively to one group.

Do not trust group identity from robot messages.

The simulator does not need to send a `group_id`.

Instead:

```text
robot_id
    ↓
lookup registered robot
    ↓
resolve group_id from PostgreSQL
```

Only clients authorized for that group may receive the WebSocket event.

A status event belonging to:

```text
Group A
```

must never be broadcast to:

```text
Group B
```

# 23. Initial End-to-End Scenario

The implementation must support:

```text
1. Robot exists in PostgreSQL.

2. Initial state:
   connection_status = OFFLINE

3. Start robot simulator.

4. Simulator connects to Mosquitto.

5. Simulator publishes:
   robot.online

6. Topic contains robot_id.

7. Payload contains matching robot_id.

8. Payload includes current IP metadata.

9. MQTT ingestion validates the event.

10. MQTT ingestion publishes an internal event to RabbitMQ.

11. RabbitMQ consumer receives it.

12. Consumer resolves robot by UUID.

13. Consumer checks Redis.

14. Consumer falls back to PostgreSQL if necessary.

15. State changes:
    OFFLINE → ONLINE

16. Redis is updated.

17. PostgreSQL is updated.

18. last_seen_at is updated.

19. IP metadata is updated if necessary.

20. WebSocket event is emitted.

21. React identifies robot by robot_id.

22. Robot card changes:
    Offline → Online

23. Kill simulator unexpectedly.

24. Mosquitto emits LWT.

25. The same pipeline processes:
    ONLINE → OFFLINE

26. React updates:
    Online → Offline
```
